Abstract
Generating HTML from natural-language spec-
ifications is an important application of code
large language models (LLMs). Despite pro-
ducing renderable pages, current models of-
ten fail to ensure functionality and visual qual-
ity during actual interaction. Existing meth-
ods typically target task-specific webpage su-
pervision, leaving demanding interactive arti-
fact optimization underexplored. Using mini-
games as a challenging testbed, we expose lim-
itations in interaction experience, reward sig-
nal, and credit assignment fidelity that are ob-
scured by shallow webpage interactions. We
introduce WebCatalyst, a browser-interaction
reinforcement learning framework with three
complementary components: a game-level GUI
assessor for sustained interaction and evalua-
tion, Visual Anchor for mitigating VLM reward
hacking, and Action-Trace Credit for ground-
ing token-level credit assignment in runtime
execution traces. Trained on fewer than 1K
requests, predominantly for games, WebCata-
lyst raises the Cookie-Bench Mini Games score
from 68.8 to 75.3 and also the WebGen-Bench
accuracy from 48.8 to 56.9 on Qwen3.6-35B-
A3B, outperforming Claude Opus 4.7 in av-
erage rank across evaluated metrics. Further
analysis shows that Visual Anchor prevents
aesthetic degradation, while runtime-grounded
credit assignment accelerates functional im-
provement. Together, our results show that im-
proving feedback fidelity is the key to substan-
tially advancing interactive HTML generation.

To this end, we introduce WebCatalyst, a

Its high-fidelity supervision addresses

interactions into effective learning signals. First,
evaluating interactive HTML requires evidence
from actual interaction (Zhang et al., 2026b; Yang
et al., 2026).
Our GUI Assessor (§3.1) con-
ducts sustained, game-level browser interactions
and hierarchically aggregates action outcomes and
screenshot-based evaluations into a page-level re-

mode in GUI-agent evaluation: VLM judges may
overlook visual degradation when functionality im-
proves. To mitigate this bias, the Visual Anchor
(§3.2) penalizes degradation relative to reference
screenshots. Third, coarse page-level rewards pro-
vide little guidance about which code tokens con-
tribute to individual behaviors in complex interac-
tive environments (Dou et al., 2024; Kumar et al.,
2026; Jin et al., 2026). We therefore introduce
Action-Trace Credit (§3.3), a runtime-grounded
credit-assignment method that captures call stacks
for successful actions, maps executed code spans
back to generated tokens, and redistributes advan-
tages according to call depth. These components
improve interaction experience, reward signal, and
credit assignment fidelity enabling more effective
training for complex interactive HTML generation.
With fewer than 1K training requests, most in-
volving games with complex interactions, Web-
Catalyst improves the Cookie-Bench Mini Games
overall score from 68.8 to 75.3 and WebGen-Bench
accuracy from 48.8 to 56.9 on Qwen3.6-35B-A3B.
It also achieves a better average rank than Claude
Opus 4.7 across webpage and mini-game evalu-
ations.
Further analysis reveals that GUI feed-
back alone improves functionality at the cost of
visual quality. Visual Anchor mitigates this degra-
dation, while Action-Trace Credit accelerates gains
on functional metrics. By exposing limitations
masked by shallow webpage interactions, these
results show how high-fidelity feedback can move
RL beyond task-specific optimization toward more
capable interactive HTML generation.
Our contributions are:
• We study interactive HTML generation be-
yond task-specific webpage optimization, us-
ing challenging mini-games to reveal three
key dimensions of RL supervision fidelity:
interaction experience, reward signals, and
credit assignment.
• We introduce WebCatalyst, a unified browser-
interaction RL framework that addresses these
limitations through three complementary com-
ponents: a Game-Level GUI Assessor, Vi-
sual Anchor, and Action-Trace Credit.
• With fewer than 1K training requests, WebCat-
alyst improves both game and webpage gener-
ation, enabling Qwen3.6-35B-A3B to achieve
a better average rank than Claude Opus 4.7
across evaluated metrics.

Related Work
2.1
Assessing Interactive HTML Artifacts
Evaluating interactive HTML requires assessing
both functional behavior and visual quality dur-
ing use. GUI agents provide grounded mouse-and-
keyboard interaction (Cheng et al., 2024; He et al.,
2024; Qin et al., 2025), but existing browser and
desktop environments mainly evaluate agents in
pre-existing applications (Zhou et al., 2024; Drouin
et al., 2024; Xie et al., 2024). For generated HTML,
interaction-aware benchmarks evaluate behavior,
functionality, and visual quality (Xiao et al., 2025;
Lu et al., 2025; Zhang et al., 2025). Recent ex-
ploratory evaluators gather visual and behavioral
evidence over interaction trajectories (Zhang et al.,
2026b; Yang et al., 2026), while game-oriented
evaluators assess runtime gameplay and sometimes
support iterative code refinement (Zhang et al.,
2026a; Huang et al., 2026; Peng et al., 2026). These
works use interactive assessors primarily for bench-
marking or inference-time refinement, rather than
as feedback providers for RL.
2.2
Training for HTML Generation
HTML generation covers design reconstruction
and web application generation from natural-
language requests. Supervised approaches learn
from screenshot–code pairs (Beltramelli, 2017;
Laurençon et al., 2024; Yun et al., 2024; Gui et al.,
2025). Browser-guided refinement also supplies
SFT data (Lu et al., 2026; Wu et al., 2026). Recent
RL methods primarily target webpage generation,
using feedback aligning with task-specific evalu-
ation protocols (Lai et al., 2025; Li et al., 2026b;
2


Jiang et al., 2026; Lu et al., 2026; Chen et al., 2026),
whereas we focus on RL supervision fidelity in sus-
tained HTML interaction.
2.3
Code Credit Assignment
Sequence-level rewards obscure the contributions
of individual code regions. Prior work localizes
feedback using learned reward models (Le et al.,
2022; Fan et al., 2026), compiler-reported errors
(Liu et al., 2023), execution coverage (Dou et al.,
2024; Kumar et al., 2026), or a single related code
span (Li et al., 2026a; Jin et al., 2026). Our Action-
Trace Credit enables precise behavior-to-code re-
ward assignment by tracing each successful GUI
action to its runtime code path.

3.3
Runtime-Grounded Credit Assignment
Even with calibrated page-level rewards, optimiz-
ers such as GRPO uniformly assign advantage Ai
to all generated tokens, obscuring which code re-
gions contribute to individual interactive behaviors.
Directly penalizing failed actions can cause mis-
attribution: a failure may arise from incorrect or
missing logic, whose responsible code can be am-
biguous or absent from the runtime trace. Thinking
in reverse, we derive Action-Trace Credit (ATC)
from the runtime call paths of successful actions.
Runtime Code Tracing.
To identify the code
responsible for individual interactions, we capture
JavaScript call stacks via the Chrome DevTools
Protocol during traceable actions, retaining only
traces from actions classified as successful by the
Step-level Judge. Each stack contains the active
leaf frame followed by its callers. Following this

4
Experiments
4.1
Experimental Setup
Benchmarks.
We evaluate HTML generation at
different levels of interaction complexity using
WebGen-Bench (Lu et al., 2025) and the Mini
Games split of Cookie-Bench (Yang et al., 2026).
WebGen-Bench contains 101 webpage-generation
requests and 647 test cases, each specifying an
operation and expected outcome to verify a func-
tional or presentation requirement. For Cookie-
Bench Mini Games, we evaluate 156 deduplicated
requests. The benchmark uses UI-TARS (Qin et al.,
2025) to continuously interact with browser, pro-
ducing visual and behavioral traces used to assess
aesthetics and functionality which tests more de-
manding interactive HTML generation.
Metrics.
For WebGen-Bench, an evaluation
agent executes each test case and compares the
observed behavior with its expected outcome, as-
signing a verdict of YES, PARTIAL, or NO. These
verdicts receive scores of 1, 0.5, and 0, respec-
tively, and Accuracy is their mean across all test
cases. We also report Accuracy by category, Con-
tent Presentation, User Interaction, Data Manage-
ment, Functional Testing, Data Display Testing,
and Design Validation Testing. Start Failure Rate
is the percentage of generated websites that fail to
launch. Lower is better.
For Cookie-Bench Mini Games, the evaluator
scores each artifact’s visual quality (Aesthetics)
and its behavior robustness over sustained inter-
action (Functionality). We average request-level
scores and report them on a 0–100 scale. Total
aggregates performance across both dimensions.

Implementation Details.
We construct the train-
ing set by collecting Reddit posts about HTML
development, filtering them with game-related key-
words, and rewriting them as direct user requests.
This allows us to test whether interactive HTML
training with high-fidelity feedback transfers to
simpler downstream tasks such as conventional
webpages. We train Qwen3.6-35B-A3B (Qwen
Team, 2026b) on NVIDIA GB200 GPUs with a
batch size of 16 and group size G = 5. For ATC,
we set β = 0.5 and the decay factor γ = 0.9. We
use GPT-5.6 Terra as the judging model in the GUI
Assessor, allowing up to eight interaction turns per
page. We use GPT-5.5 to generate Visual Anchor’s
reference artifacts. We evaluate the checkpoint
after 40 training steps, corresponding to 640 pro-
cessed requests. Further implementation details are
provided in the Appendix A.3.
4.2
Main Results
Table 1 compares WebCatalyst on Cookie-Bench
Mini Games and WebGen-Bench, representing
complex interactive artifacts and conventional web-
pages, respectively. Because our training requests
are collected using game-related keywords, Mini
Games provides a task-aligned but demanding eval-
uation. WebGen-Bench instead uses rubric-based
test cases for conventional webpages, providing
a cross-setting evaluation of whether capabilities
learned from interactive game generation transfer
to broader webpage tasks.
First, high-fidelity feedback enables compet-
itive mini-game generation. Using 640 training
requests, WebCatalyst raises the Mini Games Total
score of Qwen3.6-35B-A3B from 68.8 to 75.3. The
improvement spans both evaluation dimensions:
Aesthetics increases from 81.5 to 87.5, and Func-
tionality from 56.1 to 63.2. Despite using a rela-
tively compact backbone with 35B total parameters
and 3B activated per token, WebCatalyst outper-
forms several contemporary frontier models, in-
cluding MiniMax-M2.7, GLM-5.1, and Kimi-K2.6,
and matches Claude Opus 4.7 on the Total metric.
Second, the gains transfer to conventional
webpages with simpler operations and design
requirements. Despite being trained primarily
on game-focused requests, WebCatalyst improves
overall WebGen-Bench Accuracy from 48.8 to
56.9, with improvements across all request- and
test-case categories. Notable gains appear in User
Interaction (43.0 to 52.9), Content Presentation
(59.2 to 68.1), and Functional Testing (33.9 to
42.2), indicating that the transfer covers both exe-
cutable behavior and visual presentation. Its over-
all Accuracy exceeds Kimi-K2.6 (54.9) and nearly
matches Claude Opus 4.7 (57.0). These results
suggest that high-fidelity training on complex inter-

4.3
Ablation Study
Table 2 isolates the complementary contributions of
the three feedback-fidelity components. Adding the
GUI Assessor increases WebGen Accuracy from
48.8 to 52.2 and Mini Games Functionality from
56.1 to 60.5. However, Aesthetics drops from 81.5
to 71.3, reducing Total from 68.8 to 65.9. This
trade-off shows that unanchored GUI feedback can
reward functional improvements while overlooking
visual degradation, exposing the reward loophole.
Visual Anchor mitigates this degradation. Self
Anchor uses screenshots from the base model’s
pre-RL outputs as references, whereas GPT-5.5
Anchor uses screenshots from GPT-5.5-generated
artifacts. Both variants restore Aesthetics above
the backbone level and increase Total from 65.9 to
70.0 and 70.3, respectively, while further improv-
ing WebGen Accuracy to 55.5 and 56.8. These re-
sults show that reference-based calibration discour-
ages visual simplification while preserving func-
tional gains. Both Visual Anchor variants mitigate
reward-induced visual degradation, while further
analysis suggests that higher-quality anchors help
maintain training stability (§4.4.1).
Finally, adding the action-trace credit raises Mini
Games aesthetics, functionality, and Total from
82.3, 58.2, and 70.3 to 87.5, 63.2, and 75.3, while
preserving WebGen accuracy at 56.9. Thus, Vi-
sual Anchor and ATC play complementary roles:
the former calibrates what makes a high-quality
artifact, whereas the latter assigns the resulting
feedback more precisely to responsible tokens.

Conclusion
We introduce WebCatalyst, a unified browser-
interaction RL framework that improves supervi-
sion fidelity across interaction experience, reward
signals, and credit assignment. Trained on fewer
than 1K requests, primarily mini-games, WebCata-
lyst substantially improves mini-game generation,
with gains transferring to conventional webpage
tasks. These results underscore the importance
of high-fidelity feedback for moving beyond task-
specific webpage optimization toward more capa-
ble and general interactive HTML generation.
8


6
Limitations
While WebCatalyst enhances the interactive HTML
generation capabilities of LLMs, several aspects
remain to be explored. First, this work focuses on
direct generation. Although our experiments show
that stronger direct generation also benefits multi-
turn refinement, we do not specifically optimize
more complex pipelines involving planning, itera-
tive debugging, or tool use. Second, WebCatalyst
studies how RL activates and strengthens interac-
tive HTML capabilities already present in the base
model. It complements rather than replaces SFT,
which establishes the foundation for visual style,
animation, and artifact complexity. The effective-
ness of RL therefore remains dependent on the ca-
pabilities acquired before training. Finally, we train
our model on game prompts to examine whether ca-
pabilities learned from interaction-intensive tasks
transfer to simpler settings such as conventional
webpages. We leave the optimization of task mix-
tures and data composition, as well as their effects
on performance and generalization, to future work.
More broadly, stronger interactive HTML gen-
eration capabilities may introduce misuse risks,
including the generation of deceptive interfaces,
phishing websites, malicious client-side behaviors,
or other harmful web content. Although our work
focuses on benign generation tasks, future deploy-
ment should incorporate appropriate safety safe-
guards and misuse-aware evaluation.

A.1
GUI Assessor Pipeline
This section includes the details of our GUI Asses-
sor. Given a requirement prompt x and a sampled
HTML artifact hi, the assessor (i) executes hi un-
der controlled browser budget, (ii) chooses and
performs a sequence of user actions, (iii) evaluates
every transition as soon as it is produced, and (iv)
aggregates the completed trajectory into the page-
level score RGUI
i
. We present the overall workflow
of the GUI Assessor below, together with the key
design considerations that guide its construction.
A.1.1
Controlled Browser Execution
We load hi in a fresh Chromium context1 with a
fixed 1440×900 viewport and wait for network idle-
ness before interaction. Playwright’s virtual clock
is then paused and advanced only by the execu-
tor. This prevents uncontrolled wall-clock delays
from changing animations or game state while a
model call is in flight. At turn t, the page has la-
tent browser state Vi,t and observable screenshot
Si,t = O(Vi,t). After choosing and executing ai,t,
the browser produces Vi,t+1 = Thi(Vi,t, ai,t), the
post-action screenshot Si,t+1, and the execution
record mi,t. Together they form the transition Ei,t
defined in the main text.
Before the first turn, the mouse is moved to the
viewport center. Before every subsequent deci-
sion, the virtual clock is paused again and a full-
page screenshot is captured. An episode termi-
nates when the Execution Agent emits terminate
or when the interaction budget is exhausted.
A.1.2
Execution-Agent Context and Decision
The Execution Agent implements the ReAct-style
interaction policy. Its decision context contains
direct visual evidence, a compact history, and
browser affordances, as summarized in Table 4.
The screenshot remains the source of truth for
the current visible state. Source code is also sup-
plied only as a rules reference for identifying sup-
ported inputs, event handlers, coordinate trans-
forms, cooldowns, and pointer-lock behavior.
The agent returns a structured decision contain-
ing a one-sentence summary, one action ai,t, a pre-
dicted visible target state, an expected transition,
and optional psychometric observations. Only ai,t
is executed. The predicted target and transition

A.3.2
Training Dataset Construction
We construct the training set from Reddit posts
related to frontend and game development. We
first retrieve candidate requests using “game” and
related keywords.
We ensure that no sensitive
or personal identification information is obtained
in our data. The requests are then rewritten into
natural user-facing queries with diverse personas,
tones, and levels of constraint specificity. We apply
a broad HTML-game filter that retains examples
exhibiting a complete game subject, browser or
HTML technology, and concrete game mechan-
ics, while removing backend-only questions and
requests that do not define a playable artifact. GPT-
5.5 subsequently verifies each retained query and
either keeps it unchanged when it is already suit-
able or refines it into a direct request for a complete,
self-contained browser game. After deduplication,
the resulting prompts are split into training and val-
idation sets. At training time, each prompt is paired
with a system instruction requiring the policy to
return only one complete HTML document with
all CSS and JavaScript included inline.
A.3.3
Evaluation Protocol
Generation setup.
We evaluate the models on
the test sets of WebGen-Bench (Lu et al., 2025) and
Cookie-Bench Mini Games (Yang et al., 2026). For
every benchmark request, the model receives the
original user prompt together with the same output-
format instruction, that is, return one complete,
self-contained HTML document with all CSS and
JavaScript included inline.
For our locally served Qwen checkpoints, we use
temperature 0.6, top-p 0.95, top-k 20, a maximum
of 32,768 response tokens, and enable the model’s
thinking mode. For proprietary baselines, we retain
the provider-native sampling configuration and set
the largest supported output-token budget when
that control is available.
Cookie-Bench Mini Games.
We use the dedupli-
cated multilingual Mini Games split containing 156
requests, primarily in Chinese and English, with
additional examples in French, German, Spanish,
and other languages. Each generated HTML file is
served in Chromium and first receives provisional
aesthetics and functionality scores from its initial
rendered state. A source-aware planner then con-
structs a test plan, after which UI-TARS explores
the game through a ReAct loop. The evaluator
records the action trace and reviews it, identifies
functional and visual problems, and adjusts the
provisional scores. We use Qwen3.8-27B as the ex-
ecution model and DeepSeek-V4-Pro as the review
model. A model-side format generation, installa-
tion, or launch failure is retained with zero score.
A failed evaluator pass is retried once with a fresh
browser-agent session.

WebGen-Bench contains 101

A.4
Practical Deployment Guidance
A.4.1
Cost Breakdown
We train Qwen3.6-35B-A3B for 40 optimization
steps on eight NVIDIA B200 GPUs. The main
efficiency bottleneck is artifact evaluation by the
GUI Assessor. Our primary setting uses GPT-5.6
Terra through an API limited to 50 requests per
minute, with six concurrent assessor workers. Eval-
uating the 80 rollouts generated at each training
step takes approximately 40 minutes, correspond-
ing to an effective throughput of about 2 rollouts
per minute. As shown in Table 9, evaluating one
rollout consumes, on average, 112.27K input to-
kens and 9.28K output tokens, or 121.56K tokens
in total. A full training step therefore consumes ap-
proximately 8.98M input tokens and 0.74M output
tokens. At prices of $2 and $12 per million input
and output tokens, respectively, this amounts to
approximately $26.88 per step, or $1,075 over 40
steps, excluding caching discounts and unlogged
retries. The run takes approximately 26.7 B200
GPU-hours for LLM inference and parameter up-
dates.
On an eight-GPU A100 SXM system, the as-
sessor latency is comparable to the time required
for policy rollout generation. This suggests that
an asynchronous policy-training pipeline with a
policy staleness of approximately one step could
overlap assessment with subsequent rollouts and
improve hardware utilization. We leave such an
implementation to future work.
We additionally experiment with Qwen3.8-27B
as a locally served judge, using four B200 GPUs
for vLLM judge serving and four B200 GPUs for
rollout and training. This configuration requires
approximately 192 aggregate B200 GPU-hours for
40 steps (about 24 hours of wall-clock time), while
its token consumption is of the same order as that
of GPT-5.6 Terra. These measurements expose
both the monetary and latency costs of using our
GUI Assessor and provide practical guidance for
reproducing or scaling the training pipeline.

Combined Step-Level Evaluation
System:
You are the combined TransitionJudger and
ScreenshotJudger for an HTML game quality
evaluation system. You receive exactly two images in
this order: Image 1 is the before-action screenshot and
Image 2 is the after-action screenshot. Evaluate both

TransitionJudger:
Evaluate the two screenshots as evidence of the game’s
interaction and visual transition quality. Use action
execution and hit-test metadata to determine whether
the simulator delivered the requested action to the
intended target. Action execution warnings are
simulator diagnostics. If metadata warns that a canvas
selector click lacked coordinates, treat it as evidence
that the simulator clicked the canvas center; for a 2D
canvas internal target this is usually coordinate_miss,
not proof that the game failed to respond. If metadata
contains success=false or executionError, set
executionReward low and classify failureMode as
action_ineffective, while still judging visual stability
and app feedback from the images. The targetState,
expectedTransition, and decision summary describe
simulator intent only. Do not score whether that
prediction was fulfilled. Score the HTML game itself:
visual continuity, responsiveness, feedback clarity, rule
consistency, animation/state coherence, absence of
crashes or broken rendering, and whether the observed
transition makes sense for visible game mechanics. Use
multi-dimensional rewards. Human product-quality
preference should prioritize stable, readable, coherent
visuals and understandable feedback over immediate
task progress. Task progress is a weak component and
must not dominate overall reward. Strengths and
weaknesses must describe the game’s transition,
feedback, coherence, and robustness, not whether the
simulator’s predicted target was achieved. If hit-test
metadata shows the action point missed the intended
target, use coordinate_miss; do not conclude that the
action mechanism itself is ineffective. If the action is
invalid under visible state or ordinary app/game rules,
use illegal_or_rejected. Clear rejection can still receive
high visualStabilityReward and appFeedbackReward. If
an apparently valid, correctly delivered action produces
no feedback, state change, partial progress, or
consistent behavior, use action_ineffective; treat it as a
likely implementation bug, selector/event mismatch, or
execution-path issue and penalize it strongly. Do not
punish the app heavily just because the simulator chose
a poor action. A rejected or no-op action can still earn
Combined Step-Level Evaluation (continued)
high visualStabilityReward and appFeedbackReward
when the page remains stable and feedback is clear.
Describe the before image state compactly and extract

Transition reward dimensions:
- visualStabilityReward: rendering stability, layout
coherence, readable visuals, absence of flicker, broken
frames, crashes, or state corruption. This is the most
important reward.
- appFeedbackReward: clarity, immediacy, and
rule-consistency of the app/game response. Legal
rejection can score high when it is understandable.
- executionReward: whether the simulator delivered the
requested action to the intended element, coordinate,
key, or mouse target according to metadata.
- taskProgressReward: weakly weighted progress
toward the task/scenario, such as starting play, moving,
scoring, collecting, or completing an objective.
Compute transition overallReward = 0.40 *
visualStabilityReward + 0.25 * appFeedbackReward +
0.25 * executionReward + 0.10 * taskProgressReward.
Transition rubric:
- 90-100 overallReward: Stable, readable, coherent
visuals with clear feedback and correct simulator
execution; task progress may be partial or absent if a
no-op or rejection is understandable.
- 70-89 overallReward: Mostly stable and
understandable, with minor ambiguity, weak feedback,
or limited task progress.
- 40-69 overallReward: Usable but meaningfully weak
in feedback, execution clarity, visual stability, or
interaction coherence.
- 1-39 overallReward: Severe visual instability, broken
rendering, execution mismatch, or an apparently valid
action producing no understandable feedback.
- 0 overallReward: The two images are blank, corrupted,
missing essential page content, or impossible to
evaluate.
Transition failureMode definitions:
- "none": the action succeeded or any failure is not
relevant.
- "coordinate_miss": the action point missed the
intended target or landed on the wrong element or
region.
- "action_ineffective": the target was correct and the
action should be valid by visible state, but the app did
not respond as expected.
- "illegal_or_rejected": the action was invalid by visible
state or game rules, missing prerequisites, resource
constraints, cooldowns, distance checks, or mechanics
and was rejected or correctly no-oped.
- "timing_issue": the action is plausible but appears too
early, too late, or not held long enough.
- "uncertain": there is not enough evidence to classify
the failure.
